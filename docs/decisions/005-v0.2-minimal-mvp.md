# ADR 005: V0.2 minimal MVP scope

日期：2026-09-15。状态：已采纳。

## 背景

V0.1 已经验证「理解当前对象，再推荐动作」，但激活要等同一次完整解析，输入只能匹配自己识别出的对象，且没有应用搜索、分组或迟到 Context。V0.2 只验证五件事：Context → Context、应用搜索、统一搜索、Group/Scope、Availability。

## 决策

**统一 Provider 链。** 输入先产生 `core.text`，再由 Provider 推导 `core.url`、`json.document`、`core.file`、`core.directory`；目录再推导 `git.repository`。V0.1 的独立 Resolver 集合被同一条链取代，识别规则不变。没有互斥的输入类型判断。

**调用方控制首屏。** Provider 不感知超时，由 `Resolver` 顺序 step 并在 `first_snapshot_budget`（默认 40ms）到期时提交当前结果；到期时若仍有调用在飞，最多再等 `DEFAULT_FIRST_CONTENT_GRACE`（400ms，可关闭），因为实测 Finder Automation 目录捕获约 250ms，纯预算路径会先发布一个空 launcher。预算不取消 Provider；剩余工作在后台继续，并在通过 Session/Revision 校验后追加。被预算截断的 Provider 调用被**保留**：调用一开始就 detach 成独立任务，`ContextGraphRun` 持有它的接收端，late pass 继续等同一个结果，因此同一个 `(provider, context, session, revision)` 只会被调用一次。丢弃 future 会连带取消它内部的 `spawn_blocking` await，既丢掉已完成的工作，又迫使 late pass 重调一次 Provider。

**业务身份稳定 ID。** 候选 ID 由命令与规范对象值组成，不含列表 index；可执行性仍由 `(session, revision, candidate_id)` 校验。因此 late rerank 与 Scope 切换不会移动用户已选中的行，而旧快照的 ID 仍然不能执行。

**快照序号。** 同一 Revision 的 late enrichment 发布更高的 `snapshot_seq`；宿主拒绝更低序号，避免同版本旧首屏覆盖更新的状态。

**应用索引在 Context Graph 之外。** 后台扫描标准目录，从 bundle 读取身份；同一 bundle_id 的重复安装按稳定顺序去重；索引不持久化、不监听、不阻塞首屏，图标懒加载。

**Group 与 Scope。** 每个 Action 必须有 `group_id`，适用性只由 `accepts` 决定。Core 计算 Context 适用性、Availability、查询匹配、Ranking 和每个 Scope 的候选列表；UI 只切换预计算列表。Current App Scope 取环境来源加显式应用归属，不包含启动候选。

**Availability 只读内存。** 只允许读取已有 Context、Session 状态、剪贴板快照和当前应用；不做昂贵 IO。Hidden 不进入列表，Disabled 显示原因但不能执行。

**最小 Git 执行。** 只提供 Status/Log/Diff，固定 argv、明确仓库路径、无 shell、禁用 pager/external helper、并发读取输出、5 秒超时、1 MiB 上限。仓库发现阶段不运行 Git。

**保留 V0.1 插件与数据。** `protocol_version = 1` 继续可读，新元数据全部可选；`core.json` 在注册边界归一为 `json.document`，命令 ID 不变；历史只在读取时合并旧 JSON 行，不重写数据库，也不新增表。

## 后果

- 首屏可以在 Finder Automation 较慢时先显示已有 Context，代价是可能出现第二次视觉更新（`snapshot_seq` 递增）。
- Home 从「显示全部可滚动」变为「最多 7 条」；搜索保持可滚动。这是本版刻意的产品决定。
- 非空输入不再排除环境动作，而是要求它们匹配查询。粘贴对象仍只出现该对象的动作，普通文本搜索降到兜底位置。
- 应用索引每次进程重建，且每次激活时若尚未就绪则不再重复扫描；索引到达时会重建当前 Revision 的快照，使「打开后立刻搜应用」也能看到结果。重建只在 Revision 收敛后发布，避免把未完成的快照当作 late update。不做持久化以避免 stale 与迁移成本。
- 动作的货币性在**产生副作用之前**校验（`candidates_revision` 必须等于请求的 Revision）；副作用之后不再因失焦中止，否则会丢掉成功动作的 usage 记录。
- 三个新平台能力在 Windows 上也有实现（开始菜单 `.lnk` 索引、`CF_UNICODETEXT` 剪贴板、共用 argv 白名单的 Git runner），但只在 macOS 上通过类型检查与测试，尚未在 Windows 实机运行；UWP 应用与图标提取不在此版范围。
- 没有并行 Scheduler、Provider 分类、网络或 AI Provider。扩展现有能力前必须先测量。

## 未决

`first_snapshot_budget = 40ms`、Home 上限 7、`⌥ ← / →` 切换 Scope 都是本版验收默认值，尚无实测基线支撑；V0.2 完成后按实际使用和 profiling 再决定是否调整下一版范围。

首屏的验收口径本身也是未决项，但**已经变更过**：见下节。

## 首屏验收口径的变更（已确认）

原始需求写的是「到达 budget → 用当前结果生成首屏，不等待」。实现改为「到达 budget 时若仍有 Provider 在飞，最多再等 `DEFAULT_FIRST_CONTENT_GRACE`（400ms）」。

这是**验收标准的变更**，不是实现偏差：

| | 原始口径 | 当前口径 |
|---|---|---|
| 首屏时机 | budget（40ms）到期即发布 | budget 到期后，若仍有调用在飞，最多再等 400ms |
| 慢目录捕获（Finder，约 250ms）下的首屏 | 0 个候选，用户必须输入文字 | 直接带目录与 Git 动作 |
| 冷启动首帧 | < 100ms | 最快 < 100ms；带慢捕获时约 250–350ms |
| late pass | 补齐剩余 Context | 不变，仍在整图未完成时继续 |

理由：用户报告的第一个缺陷就是「从 Finder 唤起没有默认加载当前应用的 contextType，需要输入文字才显示 copy path 等 action」。纯预算路径必然复现该缺陷，因为它会在目录捕获返回之前发布一个空 launcher。

代价与边界：
- `hotkey_to_visible < 100ms` 这一条在带慢目录捕获时不再成立。人工清单 R05 已改为分别记录两种情况并与 grace 对照，而不是断言一个设计上不再满足的目标。
- 预算本身（40ms）没有改变，`first_snapshot_budget_reached` 仍在预算到期时记录——它由等待 grace 的那条路径发出（`core/context/engine.rs` 的 `await_outcome`），因此无论后面等多久、最终是否发布，预算到期这件事都会被如实记下；grace 只延长*等待*，不延长 Provider 的工作。`first_snapshot_grace_is_bounded_and_late_pass_still_completes` 现在断言该字段确实被发出。
- `with_content_grace(Duration::ZERO)` 可以恢复纯预算行为，测试用它覆盖那条路径。
- 要回到原始口径，把 `DEFAULT_FIRST_CONTENT_GRACE` 设为 `Duration::ZERO` 即可，代价是重新接受「打开后先看到空 launcher」。
