# 外部评审建议复核与取舍

日期：2026-10-23。审查输入为用户提供的《Anywhere 项目评审与发展建议》v1.0，报告基线为 `4ea207b` / V0.12 Build 15。本轮对照当前工作树、现行设计与 GitHub Release 元数据进行复核；工作树还包含上一轮已通过工程检查、尚未提交的旧接口清理。本次只形成建议排期，没有实施新功能、修改 GitHub Release 或完成 GUI / 性能验收。

**结论：采纳报告的收敛方向，调整新增范围与顺序。** 继续使用 Flutter / Rust / Native Host、静态内置模块与按需 WebView，优先保障日常工作流、隐私和可验证的交付。后续版本建议维护在[产品路线图](../roadmap.md)，本页只记录取舍依据。

同日用户进一步明确：Recent Projects 扩大为跨应用的“应用历史与收藏”，包括浏览器历史 / 书签、IDEA / VS Code 最近项目、Obsidian 最近笔记等。已纳入 V0.14；这取代单独的 Recent Projects 新功能定义，不改变外部报告原文，设计与可行性见[专题](../application-history.md)。

## 1. R01–R10 的处理

| 建议 | 判断 | 采纳方式 |
|---|---|---|
| R01 最新 Release 入口 | 立即采纳 | 远端 `latest` 仍指向 2026-09-18 的 dev-0.3 合并提交 `5b6056f`，名称为 Latest build，附 macOS 和 Windows 包。先明确历史状态和当前下载边界；下一次从不可变版本 tag 交付，保留旧版本可追溯性 |
| R02 最新构建实机验收 | 立即采纳 | 以一个明确 SHA / 构建完成输入法、焦点、菜单、权限和主要页面矩阵。已有自动化和历史实机结果继续复用，补当前缺口；不逐版本重抄整份检查表 |
| R03 签名 / 公证 / 升级 | 分阶段采纳 | 本机开发继续使用稳定签名。面向外部的版本再完成 Developer ID、公证和干净机器升级 / 回退；1.0 可使用经过验证的手动升级，不要求同时开发自动更新系统 |
| R04 剪贴板隐私 | 采纳真实增量 | 先做定时暂停、保留期限与明确存储说明。已有启停、敏感格式过滤和数据库 secure_delete 继续复用。应用排除先验证来源身份能力，不能用当前前台 App 冒充实际复制来源 |
| R05 端到端性能 | 立即采纳 | 先建立当前构建的同机场景基线，再确定优化目标。包括首帧、首个可用结果、查询呈现、主进程 / helper、反复打开和长时间运行；不先承诺未经测量的毫秒 / MiB 数字 |
| R06 插件开发体验 | 采纳，拆小 | 先交付浏览器 Mock、统一诊断和兼容表，再考虑受控开发预览。独立模板、两个示例和 Manifest / 包检查已存在；完整 HMR 不作为 1.0 必需项 |
| R07 Flutter 协调器解耦 | 按问题推进 | 大文件值得关注，但行数不是重写依据。已有 Session、Activation、Workspace、Shortcut 和 HostView 协调器；只迁移实际拥有独立状态 / 生命周期且有回归约束的职责 |
| R08 Context 并发 | 保留研究，暂不改执行模型 | Provider 派生串行属实；环境采集另有独立任务。先测具体慢点，再比较小范围有界并发；没有收益证据则保持当前机制 |
| R09 第三方 ContextProvider | 延后到 1.0 之后 | 现有调研已覆盖类型所有权、输入授权、句柄、撤销和 worker。先有真实插件用例，再形成公开协议；不提前增加空注册接口或常驻 QuickJS |

## 3. 建议废弃或改变的做法

1. **废弃固定 30 / 60 / 90 天和 1.1 / 1.2 / 1.5 的远期承诺。** 没有团队容量和实测数据支撑，改为有范围、产物和退出标准的阶段。版本号表示顺序。
2. **不把亮 / 暗双主题和自动更新加入本轮必需功能。** 先验收现有共享材质在浅色 / 深色桌面、大字号和辅助功能设置下的可读性；手动升级先闭环。主题系统与自动更新均需独立需求和成本判断。
3. **不在每条候选上长期增加来源、类型和执行条件。** 这会与当前精简 UI 目标冲突。自动填入区域保留来源；有歧义、失败或用户主动查看详情时解释。身份和权限不依赖显示标签。
4. **不根据行数规定新增四个 Coordinator，也不机械删除 async / Arc / 原生适配。** 以状态所有者、依赖方向、取消和执行正确性为依据；Google 规范也按语言与项目约束落实，不照搬其他产品的专用规则。
5. **不把 Provider 派生串行误读成所有 Context 来源串行。** [context_capture](../../crates/anywhere-core/src/application/context_capture.rs) 已分别启动来源任务；[engine](../../crates/anywhere-core/src/core/context/engine.rs) 才是一次派生只等待一个 Provider。两段要分别测量。
6. **不提前实现闲置 Provider 协议、QuickJS worker 或通用后台运行时。** 先保留研究和边界，以两个真实用例决定公开贡献模型；Core 继续不感知具体脚本引擎。
7. **不以“后台 Context Runtime”重新制造另一套主流程。** 未来 worker 只是受控执行适配器，结果验证后仍进入同一 Graph / Action / Ranking。
8. **不一次性开启任意 localhost HMR、网络、文件和 Shell 能力。** 浏览器 Mock 可先独立工作；连接真实 Host 的开发目录 / 服务要有明确的工作区信任和来源策略，Manifest / 权限变化重批。

这些取舍不否认后续需求，只是不将尚无验证价值的复杂度带入当前版本。

## 4. 报告还需补充的三个边界

### 4.1 Web 包逻辑身份与安装信任连续性

[WebCommandRef::action_id](../../crates/anywhere-core/src/core/action/web_command.rs) 使用 `web:<pluginId>:<commandId>`；[安装更新](../../crates/anywhere-core/src/application/web_plugins/packages.rs) 明确本地身份连续性不等于发布者签名。现有 KV 按来源隔离，更新需要批准，但快捷键 / Usage 的逻辑身份没有发布者所有权。

这不是已经证明的授权绕过。扩大第三方使用范围前，应明确定义同名替换、卸载再安装、来源变化和未来发布者迁移如何影响旧快捷键 / Usage / KV：未知连续性默认不继承可执行绑定，拒绝模糊迁移。稳定身份不能直接使用每次变化的内容摘要，否则正常更新也会丢失连续性。

### 4.2 应用排除需要可靠的来源定义

当前 [ClipboardPayload](../../crates/anywhere-platform/src/clipboard.rs) 只含格式和数据，尚无已验证的复制来源身份。前台 App 不一定就是实际写剪贴板的进程。

应先核对各平台能提供的证据，再定义产品行为。若只实现“指定 App 在前台时暂停”，必须如实命名；不能承诺“该 App 的所有复制永不记录”。来源不确定时的处理和系统敏感标记的优先级需明确。已有 App 排除设置也不能不经核对就当作剪贴板排除。

### 4.3 收尾必须结束，验收资料要能维护

不把每一次“最后 review”都变成全新重构。选定候选构建，冻结功能范围；已确认阻断缺陷修复并复验，非阻断事项进入后续工作包。每次验收记录构建 SHA、设备、操作、结果与未覆盖项，不复制整份产品说明，不提交用户内容和原始敏感日志。

## 5. 执行方式

- 先完成一个小工作包的实现、自动化和构建，再做其对应 GUI 验收；保持既有“先单元测试、后实机”的顺序。
- 隐私、性能、插件 DX 都复用当前端口。新数据策略进入 Rust 服务；Flutter 负责交互 / 说明；平台层提供来源证据；SDK Mock 不模拟成真实授权。
- 代码规范、纯格式化、行为修复分开提交，避免审查中看不清真正的功能变化。评审后的 0.12.x 已接入[规范与自动检查](../code-style.md)；该后续落实记录不改变本页对原扫描结论的取舍。
- 不为计划中的每个名词建立空接口或提前增加依赖。每个架构改造必须绑定一个真实用例或已复现问题。
- 新排期见[产品路线图](../roadmap.md)。本次没有创建 GitHub Issues、发布新版本或改变生产权限。
